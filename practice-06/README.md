## 1. Цель работы

Освоить подключение браузерного интерфейса к учебному HTTP API: выполнение запросов через `fetch`, обработку Promise и `async`/`await`, различение HTTP-, сетевых и форматных ошибок, защиту от устаревших ответов, повторную загрузку после мутаций. Итоговый результат — приложение, которое создаёт, редактирует, удаляет задачи и меняет их статус только через запросы к серверу, без `localStorage`.

## 3. Реализация

### 3.1. HTTP-клиент

`src/api-client.js`:

- `buildUrl` — соединяет `baseUrl`, путь и `query` через `URL` и `URLSearchParams`, пропускает `undefined`, `null` и пустые строки, сохраняет `false` и `0`.
- `createApiClient` — фабрика с конфигурацией `{ baseUrl, fetchFn, timeoutMs }`.
- `requestJson(path, { method, query, body, signal, timeoutMs })` — выполняет GET, POST, PATCH или DELETE. Для GET запрещено тело, для остальных — при наличии `body` добавляется `Content-Type: application/json` и `JSON.stringify`.
- `Accept: application/json` передаётся во всех запросах.
- `AbortSignal.timeout` объединяется с внешним сигналом через `AbortSignal.any`.
- `response.ok === false` → `ApiError` с `kind: "http"` до проверки `Content-Type`.
- Статус `204` → `null` без попытки читать JSON.
- Остальные ошибки: `network`, `timeout`, `aborted`, `invalid-response` (неверный `Content-Type` или битый JSON).

### 3.2. Доменный API

`src/task-api.js` реализует 9 методов:

| Метод ↕▾                                | HTTP ↕▾                                  | Проверка ↕▾                                                          |
| --------------------------------------- | ---------------------------------------- | -------------------------------------------------------------------- |
| −`getTasks(filters, {signal})`          | GET `/tasks`                             | нормализация фильтров, схема задачи, уникальность `id`, `meta.total` |
| `getTaskById(id, {signal})`             | GET `/tasks/:id`                         | схема одной задачи                                                   |
| `getCategories({signal})`               | GET `/categories`                        | схема категорий                                                      |
| `loadInitialData(filters, {signal})`    | `Promise.all([getTasks, getCategories])` | обе схемы                                                            |
| `createTask(draft, {signal})`           | POST `/tasks`                            | схема созданной задачи                                               |
| `updateTask(id, changes, {signal})`     | PATCH `/tasks/:id`                       | схема обновлённой задачи                                             |
| `setTaskCompleted(id, value, {signal})` | PATCH `/tasks/:id`                       | `completed` — строго boolean                                         |
| `deleteTask(id, {signal})`              | DELETE `/tasks/:id`                      | ожидается `null` (204)                                               |
| `resetDemoData()`                       | POST `/debug/reset`                      | проверка `data.reset === true`                                       |

⚙

Неверная схема оборачивается в `ApiError({ kind: "invalid-response" })`.

### 3.3. Состояния интерфейса

`createAppController` управляет четырьмя состояниями:

- `loading` — при старте и при новой загрузке.
- `ready` — есть хотя бы одна задача.
- `empty` — запрос успешен, но массив пуст.
- `error` — запрос завершился `ApiError` (кроме `aborted`), показывается сообщение и кнопка `Повторить загрузку`.

Повторная загрузка через `retry` вызывает `loadInitialData`, если категории ещё не были загружены (первый запуск упал с `network`), иначе — `getTasks`.

### 3.4. Изменение данных

- `submit(draft)` — валидация через `validateTaskDraft`, затем `createTask` или `updateTask`, очистка формы, `reloadList()`.
- `toggleTask(id)` — `setTaskCompleted(id, !current)`, затем `reloadList()`.
- `deleteTask(id)` — `deleteTask`, сброс режима редактирования, если он был, `reloadList()`.
- `resetData()` — `resetDemoData()` + `reloadList()`.
- На время мутации `view.setMutationPending(true)` блокирует кнопки формы и карточек.

### 3.5. Защита от устаревшего ответа

При каждом новом запросе:

1. Предыдущий `AbortController` вызывается через `abort()`.
2. `requestSeq` увеличивается.
3. Ответ, вернувшийся с устаревшим `seq`, игнорируется.
4. `ApiError` с `kind: "aborted"` не показывается пользователю.

Это защищает интерфейс от ситуации «пользователь быстро нажал три фильтра, ответ пришёл на первый запрос».

## 6. Ответы на контрольные вопросы

1. **Почему `fetch` не отклоняет Promise при ответе 404?**
   `fetch` отклоняется только при сетевых ошибках и отмене. Ответ с любым статусом — это успешный `Response`. Проверка `response.ok` обязательна, потому что `404` — это не ошибка транспорта, а ошибка контракта, которую клиент классифицирует как `ApiError({ kind: "http", status: 404 })`.
2. **Почему ответ 204 нельзя разбирать через `response.json()`?**
   У 204 нет тела. `response.json()` в этом случае выбросит `SyntaxError` на пустой строке. Клиент проверяет статус и возвращает `null` до попытки чтения.
3. **Чем состояние `empty` отличается от `error`?**
   `empty` — запрос прошёл, но сервер вернул пустую коллекцию. Пользователь может изменить фильтры, и появятся задачи. `error` — запрос не выполнился (сеть, сервер, формат). Данные неизвестны; нужно повторить или исправить условия. Интерфейс показывает разные сообщения и разные действия.
4. **Зачем отменять предыдущий запрос при смене фильтров?**
   Пользователь может быстро переключить фильтры. Без отмены ответы придут в произвольном порядке, и на экране окажется результат не того фильтра, который выбран сейчас. `AbortController` + проверка `seq` гарантируют, что применится только последний запрос.
5. **Почему после мутации список повторно запрашивается у API?**
   Сервер — единственный источник истины. После POST/PATCH/DELETE сервер мог применить нормализацию (`trim`), изменить `id`, поменять поля, отфильтровать запись. Локальное обновление массива дало бы расхождение с сервером, особенно с учётом текущих фильтров (например, задача стала `completed: true` и больше не подходит под фильтр). Повторный GET выравнивает состояние.

## 7. Вывод

Связь между браузерным интерфейсом и API строится в три уровня:

1. **Транспорт (`api-client.js`)** — не знает про задачи, отвечает за HTTP, JSON, ошибки и отмену.
2. **Домен (`task-api.js`)** — знает маршруты и схему данных, преобразует ответы в валидированные объекты.
3. **Контроллер (`app-controller.js`)** — знает про состояние интерфейса, фильтры, редактирование и последовательность операций. Не обращается к DOM напрямую.

Такое разделение позволило:

- проверить транспорт с подменённым `fetch` без сети;
- проверить домен с подменённым клиентом без HTTP;
- проверить контроллер с fake-API и fake-view без DOM;
- проверить весь стек на реальном API в интеграционных тестах.

Найденные в процессе ошибки:

- **Преждевременная обработка `204`.** Если читать `response.json()` до проверки статуса 204, получили бы `invalid-response` на успешном DELETE. Решение: отдельная ветка для 204.
- **Широкий `try` вокруг `fetch` и обработки ответа.** HTTP-ошибка, брошенная после `fetch`, попадала в `catch` для сетевых ошибок и получала `kind: "network"`. Разделил: `fetch` — отдельный `try`, обработка `Response` — после.
- **Устаревший ответ после смены фильтра.** Первый запрос возвращался позже второго и перезаписывал актуальные данные. Решение: `AbortController` + `requestSeq` + игнорирование ответов с устаревшим seq.
