## Организация кода

| Файл                | Ответственность                                                                          |
| ------------------- | ---------------------------------------------------------------------------------------- |
| `api/server.mjs`    | Учебный HTTP-сервер, предоставлен, не меняется.                                          |
| `src/api-client.js` | Транспорт: URL, `fetch`, статус, `Content-Type`, JSON, тайм-аут, отмена, `ApiError`.     |
| `src/task-api.js`   | Доменный слой: маршруты `/tasks` и `/categories`, валидация фильтров и схемы.            |
| `src/variant.js`    | Конфигурация варианта — только данные, без ветвлений.                                    |
| `src/main.js`       | Консольный сценарий: конфигурация клиента, вызов доменного API, вывод, обработка ошибок. |

**Почему `fetchFn` передаётся в `createApiClient`.** Модульные проверки подменяют `fetch` на фейк, возвращающий подготовленный `Response`. Без явной передачи функцию пришлось бы подменять на глобальном объекте, что хрупко. Интеграционные тесты подают настоящий `globalThis.fetch`.

**Почему HTTP-ошибки проверяются отдельно от сетевых.** `fetch` не отклоняет Promise при 404 или 503 — сервер доступен и прислал ответ. Отклонение возникает только при сетевом сбое или отмене. Если весь код в одном `try`, HTTP-ошибка, созданная после `fetch`, попадёт в общий `catch` и получит неверный `kind`.

**Почему JSON проверяется по контракту после разбора.** Синтаксически корректный JSON может быть `{"data":"не массив"}` или содержать задачи с `completed: "нет"`. Клиент без проверки схемы вернул бы такие данные в приложение, и `renderTaskList` упал бы уже на отрисовке — далеко от источника ошибки.

| Требование                   | Как реализовано                                                                     | Проверка                                                                         |

| Нормализация `baseUrl`       | `assertBaseUrl` удаляет завершающий `/`, проверяет протокол и отсутствие query/hash | `createApiClient` бросает `TypeError` на относительный URL, `ftp:`, URL с `?x=1` |

## Последовательная и параллельная загрузка

Сравнение на `/debug/delay?ms=150`:

| Сценарий                     | Запуск 1, мс | Запуск 2, мс | Запуск 3, мс | Наблюдение          |
| ---------------------------- | -----------: | -----------: | -----------: | ------------------- |
| Два последовательных `await` |         ~305 |         ~302 |         ~308 | Сумма двух задержек |
| `Promise.all`                |         ~155 |         ~152 |         ~158 | Максимум из двух    |

Измерения зависят от компьютера. Причина не в «ускорении JavaScript», а в том, что при `Promise.all` оба `fetch`-запроса стартуют до первого `await`, и второй сетевой обмен выполняется, пока идёт первый. Оба запроса выполняются параллельно на сетевом уровне.

## Отладка

Точки останова в `requestJson`:

1. На строке `const url = buildUrl(...)` — для успешного запроса `/tasks?completed=false&priority=high` видно `url = "http://127.0.0.1:5505/api/tasks?completed=false&priority=high"`.
2. После `await fetchFn(...)` — `response.status === 200`, `response.ok === true`, `Content-Type: application/json`.
3. Перед `return await response.json()` — `payload = {data: [...], meta: {total: 3, filters: {...}}}`.
4. В `catch` для `getTaskById(999)` — `error.kind === "http"`, `error.status === 404`, `error.code === "TASK_NOT_FOUND"`, `error.details === {id: 999}`.

## Вывод

В работе разведены шесть видов ситуаций, которые легко спутать:

1. **Успешный ответ** — `fetch` вернул `Response`, `response.ok === true`, `Content-Type` содержит `application/json`, тело успешно разобрано и соответствует схеме.
2. **HTTP-ошибка** — `fetch` вернул `Response`, но `response.ok === false` (404, 503). Сетевой запрос прошёл успешно; проблема в самом ответе сервера.
3. **Сетевая ошибка** — `fetch` отклонился (нет соединения, DNS, отказ). Никакого `Response` не получено.
4. **Неверный ответ** — сервер ответил `200`, но `Content-Type` не `application/json`, тело не парсится или схема не соответствует модели.
5. **Тайм-аут** — сработал `AbortSignal.timeout`. `fetch` отклонился, но причина — истечение времени, а не сетевая ошибка.
6. **Отмена** — сработал внешний `AbortController`. Отмену инициировал вызывающий код, а не таймер.

Наиболее показательная ошибка, которой удалось избежать: если весь `requestJson` обёрнут в один `try` от `fetch` до `return`, то `ApiError` из HTTP-ветки попадёт в `catch`, предназначенный для сетевых сбоев, и получит `kind: "network"` вместо `kind: "http"`. Именно поэтому `fetch` вызывается в отдельном `try`, а обработка `Response` — уже после него.

Вторая ошибка — считать, что `Promise.all` параллелит операции сам по себе. Он лишь ожидает уже переданные Promise. Параллельность возникает потому, что оба `fetch` стартовали до общего `await`. Если передать в `Promise.all` не вызовы, а функции без `()` — запросы вообще не начнутся.
